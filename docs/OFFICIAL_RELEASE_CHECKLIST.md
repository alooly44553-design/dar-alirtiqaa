# قائمة متطلبات الإصدار الرسمي والإطلاق العام

## ما هو منشور حاليًا

- الموقع التقدمي (PWA) يعمل على رابط الإنتاج الرسمي، ويُعرض الإصدار 1.1.6.
- حزم البناء المعتادة في GitHub Actions هي نسخ Debug للاختبار فقط؛ لا توصف بأنها إصدار Android رسمي.
- يجهز مسار الإصدار الرسمي ملف APK موقّعًا للتثبيت المباشر وملف AAB موقّعًا للنشر عبر متجر، لكنه يتوقف عمدًا إذا كانت أسرار التوقيع غير موجودة.

## 1. إكمال توقيع Android الرسمي

يجب على مالك المؤسسة أو مسؤول الإصدار إعداد مفتاح توقيع دائم وآمن. إذا سبق نشر التطبيق بمفتاح رسمي، فيجب استعمال ذلك المفتاح نفسه؛ لا تنشئ مفتاحًا جديدًا بدلًا عنه، لأن ذلك قد يمنع التحديث فوق النسخ المنشورة.

في جهاز إداري موثوق وغير مشترك، أنشئ مفتاحًا فقط إذا لم يكن للمؤسسة مفتاح معتمد سابقًا. سيطلب `keytool` كلمات المرور بشكل تفاعلي:

```bash
keytool -genkeypair -v -keystore dar-alirtiqaa-release.jks -alias dar-alirtiqaa-release -keyalg RSA -keysize 4096 -validity 10000
```

بعد ذلك، خزّن ملف المفتاح احتياطيًا في مخزن مشفّر تتحكم فيه المؤسسة، وحوّل محتواه إلى Base64 محليًا لإدخاله سرًا في إعداد GitHub Actions. لا ترفع ملف المفتاح أو كلمات مروره إلى المستودع ولا ترسلها في المحادثات.

أضف الأسرار الأربعة في المستودع: **Settings → Secrets and variables → Actions**:

- `ANDROID_KEYSTORE_BASE64`: محتوى ملف المفتاح بعد Base64.
- `ANDROID_KEYSTORE_PASSWORD`: كلمة مرور ملف المفتاح.
- `ANDROID_KEY_ALIAS`: الاسم الذي أُنشئ للمفتاح.
- `ANDROID_KEY_PASSWORD`: كلمة مرور المفتاح الخاص.

بعد حفظ الأسرار والتحقق من ملكية المفتاح، ادفع وسم إصدار مطابقًا لنسخة `package.json`، مثل `v1.1.6`. مسار `Official signed Android release` يتحقق من الوسم، ويبني APK وAAB، ويوقعهما، ويتحقق من التوقيع، ثم يرفعهما إلى صفحة إصدارات GitHub. لا يُنشئ هذا المسار إصدارًا قابلًا للتوزيع إذا غاب أي سر أو فشل التوقيع.

## 2. بوابات يجب استكمالها قبل إعلان اكتمال التشغيل المؤسسي

هذه أعمال فعلية لا يمكن اعتمادها من تغييرات الواجهة أو من نجاح البناء وحده:

1. **المستخدمون والصلاحيات:** لا توجد روابط حسابات موثقة بين سجلات الموظفين/المتعلمين ومستخدمين Auth حتى تاريخ الفحص. يجب إنشاء/دعوة الحسابات الحقيقية وربطها ومراجعة صلاحيات الإدارة والمعلم والطالب وولي الأمر واختبار العزل بين الأدوار. لا تُنشأ حسابات وهمية في الإنتاج.
2. **مصادقة آمنة:** تفعيل حماية كلمات المرور المسربة في إعدادات Supabase Auth، ثم إجراء مراجعة أمنية للدالتين المميزتين `public.act_on_edu_directive` و`public.create_edu_directive`. لا تُلغَ صلاحياتهما عشوائيًا لأن لوحة الإدارة تستخدم RPC؛ يجب الحفاظ على فحوص الدور والمستلم وسجل التدقيق واختبارها.
3. **الخصوصية والشروط:** استبدال مسودتي `privacy.html` و`terms.html` بنصوص معتمدة قانونيًا تتضمن اسم الجهة ووسائل التواصل والاختصاص القضائي وسياسة الاحتفاظ والحذف ومشاركة البيانات، ثم اعتمادها من الإدارة.
4. **Zoom:** بيانات ربط Zoom المطلوبة لإنشاء الاجتماعات غير موجودة ضمن متغيرات بيئة إنتاج المنصة. على مسؤول الحساب توفير الاعتمادات الرسمية وتخزينها كأسرار ثم اختبار الإنشاء والتحديث والإلغاء.
5. **الرسوم:** يوجد بند تسجيل يظهر على أنه يتطلب عرض سعر/اعتمادًا إداريًا ولا يحتوي مبلغًا ثابتًا. يجب اعتماد المبلغ أو سياسة عرض السعر قبل تحصيل أي مبلغ.
6. **النسخ الاحتياطي:** تنفيذ نسخ احتياطي قابل للاستعادة واختبار استعادة موثق على بيئة منفصلة قبل اعتماد الجاهزية التشغيلية.
7. **الاختبار المتكامل:** تجربة تقديم ناجحة كاملة في بيئة اختبار تشمل التسجيل والخدمات وحفظ الطلب ووصوله إلى الإدارة ومراجعته بأدوار حقيقية. لا تُنشأ معاملات زائفة في قاعدة الإنتاج لهذا الاختبار.
8. **المرفقات:** لا تُفعّل الملفات الحساسة قبل اكتمال ربط تخزين خاص بسياسات وصول واحتفاظ مناسبة.

تبقى طلبات الخدمة والتسجيل والمهام الموجودة في قاعدة الإنتاج خاضعة لمراجعة مسؤول مخوّل. لا تُحذف أو تُعتمد أو تُرفض تلقائيًا ضمن عملية إصدار التطبيق.
