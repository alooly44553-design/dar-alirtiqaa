## 1. النتيجة التنفيذية الحالية

### ما تم التحقق منه

- سجلت Vercel حالة `READY` للنشر الإنتاجي على الالتزام المذكور.
- نجح فحص الإنتاج في GitHub Actions: **43 فحصًا ناجحًا، صفر فشل** في تشغيل 23 أكتوبر 2026.
- أعادت الصفحات العامة وبوابات التعليم والإدارة والأصول الثابتة التي شملها الاختبار حالة HTTP 200.
- أعادت واجهة حالة التعليم أن قاعدة Neon متصلة، وأعادت واجهة كتالوج الخدمات ثماني خدمات.
- رفضت واجهات إنشاء التسجيلات وطلبات الخدمات طرق GET غير المسموح بها، وأشارت إلى POST فقط.
- أعادت واجهات الإدارة وواجهة اجتماعات Zoom حالة 401 عند طلبها دون جلسة، ورفضت واجهات التسجيل وطلبات الخدمات الطلبات التي لا تتضمن الموافقة الإلزامية، دون إدخال سجل.
- نجحت اختبارات الجودة المصدرية، واختبارات مساعد Telegram، وفحص صياغة JavaScript (22 ملفًا و6 وحدات مضمنة حسب سجل التشغيل).
- نجح بناء Android من نوع Debug للاختبار، ونجح سير نشر صفحات GitHub.

### ما لا ينبغي وصفه بأنه مكتمل بعد

1. لم يثبت هذا الفحص العام نجاح تسجيل دخول من البداية إلى النهاية لحساب حقيقي مخول لكل دور (الإدارة، المعلم، الطالب، ولي الأمر) واختبار العزل بين حسابين.
2. لا يثبت اختبار رفض الطلبات غير الصالحة نجاح دورة قبول طلب صالح من البداية للنهاية؛ يجب إجراء ذلك بحساب اختبار وبيئة معزولة لا بإنشاء بيانات تجريبية في الإنتاج.
3. لم يظهر إعداد Zoom OAuth ضمن متغيرات بيئة مشروع Vercel التي فُحصت دون فك تشفير القيم؛ إنشاء الاجتماعات الفعلي غير معتمد حتى إعداد الحساب المخول واختباره.
4. نجاح Debug APK لا يساوي إصدار Android موقّعًا وجاهزًا للتوزيع. يجب اختبار الإصدار الرسمي بعد استخدام مفاتيح التوقيع الحالية المخولة والتحقق من التوقيع والتثبيت والتحديث.
5. صفحة الخصوصية وشروط الاستخدام ما زالتا موصوفتين في المشروع بأنهما مسودتان وتحتاجان اعتمادًا مناسبًا قبل الإطلاق العام النهائي.
6. ما زالت نتائج مستشار Supabase تتضمن تحذيرات أمنية وأدائية موثقة أدناه؛ تفعيل RLS على جميع الجداول المفحوصة لا يغني عن مراجعة سياسات الصفوف ودوال قاعدة البيانات.

هذه البنود بوابات استكمال موثقة وليست إيقافًا للمشروع. يمكن تشغيل الوظائف التي اجتازت اختبارات الإنتاج ضمن حدودها الحالية، مع عدم تقديم التكاملات غير المثبتة على أنها فعالة.

| الدور | المسؤوليات الرئيسية | حدود التفويض |

| المستفيد/مقدم الطلب | استعراض البرامج، تقديم بيانات لازمة، الموافقة، حفظ رقم الطلب ومتابعة حالته | لا يعني الاستلام قبولًا نهائيًا أو ضمان توفر مقعد |
| القبول والتسجيل | مراجعة اكتمال الحقول والموافقات، فرز الطلبات، طلب الاستكمال، إعداد توصية | قبول أو رفض الطلب النهائي من مسؤول مخول وبأثر مسجل |
| الإدارة التعليمية | اعتماد القرارات والسياسات والجداول وتوزيع الصلاحيات والمتابعة | القرارات عالية الأثر لا تُفوّض لمساعد آلي |
| مدير الفرع | متابعة طلبات ونشاط الفرع واحتياجات التشغيل ضمن نطاق المركز | لا يطّلع على بيانات الفروع الأخرى إلا بصلاحية |

| المعلم/المعلمة | تقديم الدروس والواجبات، متابعة الحضور والتسليم، إعداد التقييمات والتغذية الراجعة | الاطلاع على الفصول والطلاب المكلف بهم فقط؛ اعتماد الدرجة وفق الإجراء |
| الطالب | عرض الدروس والمهام، التسليم، متابعة الملاحظات والنتائج المعتمدة | الاطلاع على ملفه وسجله فقط |
| ولي الأمر | متابعة المتعلمين المرتبطين بحسابه، والاطلاع على المعلومات المسموح بها | قراءة محدودة حسب العلاقة والصلاحية؛ لا تعديل لدرجات المعلم |
| شؤون الطلاب والخدمات | تنظيم طلبات الخدمات والرسوم والمواعيد ومتابعة الاستكمال | استخدام بيانات مصدرية؛ لا اعتماد دفع أو إعفاء دون صلاحية |
| الموارد البشرية | تنظيم بيانات الطواقم والتكليفات والحضور والتدريب وسجلات الأداء | التوظيف والعقود والرواتب قرارات إدارية مستقلة |
| المالية | متابعة تعريف الرسوم والعمليات المالية والتقارير والتسويات | لا تغيير للرسوم أو تسجيل دفع غير مثبت أو إجراء رد مالي دون اعتماد |
| مسؤول الجودة والامتثال | تدقيق اكتمال السجلات، مراجعة المؤشرات، توثيق المخاطر والاختبارات والحوادث | لا يحوّل التحذير إلى شهادة امتثال دون دليل |
| مسؤول المحتوى والتواصل | إعداد محتوى البرامج، تقويم النشر، متابعة الاستفسارات والحملات | الإرسال أو النشر الخارجي يخضع للموافقة والقناة والصلاحية |

| منسق الاجتماعات الافتراضية | إعداد أجندة ومحضر وسجل حضور وتجهيز الاجتماع | إنشاء اجتماع خاص مرهون بحساب Zoom وتكامل OAuth فعال |
| مسؤول النظام والأمن | إدارة النشر، إعدادات الاستضافة، مراقبة الأخطاء، المصادقة، النسخ الاحتياطي والاستعادة | الأسرار في مخزنها المخصص فقط؛ لا تُنسخ إلى المستودع أو السجلات |

يجب أن يكون لكل حساب شخصي دور محدد، ومركز/فرع عند الاقتضاء، وحالة نشاط، ومسؤول مخول. لا تُستخدم حسابات مشتركة للأدوار الحساسة.

## 4. الخدمات والمسارات التشغيلية

### أ. البرامج التعليمية

- الطفولة والتأسيس.
- التعليم الأساسي والعام.
- التعليم الجامعي والعالي.
- التدريب المهني والتقني.
- القرآن والدراسات الإسلامية.
- التقوية والعربية والتأهيل.
- الإرشاد الأكاديمي والمهني.
- التعليم الإلكتروني والتعلم المستمر والأنشطة والفعاليات.

لكل برنامج سجل يحدد الاسم والوصف والفئة المستهدفة والمتطلبات والرسوم المعتمدة إن وجدت وطريقة التقديم والوثائق اللازمة والجدول والمسؤول وحالة الإتاحة ومصدر اعتماد المحتوى. لا يُعلن عن اعتماد أو شهادة رسمية أو شراكة مع جهة ما لم يوجد مستند صالح لذلك.

### ب. استقبال الطلبات

المسار القياسي:

1. يختار المستفيد الخدمة/البرنامج من الكتالوج المنشور.
2. يقرأ الإشعار وبيان الموافقة المتعلق بنوع الطلب.
3. يرسل الحقول المطلوبة فقط عبر نموذج المنصة.
4. يتحقق الخادم من الطريقة والموافقة وبنية البيانات والقيم المسموح بها.
5. يُحفظ الطلب عبر المسار الخلفي المعتمد، ويُولد الرقم المرجعي إن كان المسار ينص على ذلك.
6. يراجع القبول أو مسؤول الخدمة اكتمال الطلب، ويميز بين «جديد» و«ناقص» و«قيد المراجعة» و«بانتظار إجراء» و«مقبول» و«مرفوض» و«مغلق» وفق حالات النظام الفعلية.
7. تُسجل أي إعادة طلب للمعلومات أو توصية أو قرار مع صاحبه ووقته وسببه.
8. يُخطر المستفيد عبر قناة موصولة ومصرح بها فقط.
9. بعد الإكمال، تُحدّث الحالة وتُحتسب المؤشرات من السجل المصدر.

يؤكد الاختبار الأخير عمل كتالوج الخدمات وواجهات POST وحماية غياب الموافقة. ولا يتضمن هذا الاختبار إدخال طلب صحيح في الإنتاج؛ يُختبر ذلك في بيئة معزولة أو ضمن إجراء قبول مُعتمد.

### ج. دورة التعليم

`برنامج ← مرحلة/مقرر ← فصل ← معلم مكلف ← خطة درس ← درس/مورد ← واجب أو نشاط ← تسليم ← تقييم ومراجعة ← نتيجة معتمدة ← تقرير تقدم`

لا يُعرض التقييم النهائي للطالب قبل اعتماده وفق سياسة المؤسسة. يجب أن ترتبط كل درجة أو ملاحظة بهوية القائم بالإجراء وتاريخها والمقرر والفصل، مع سجل مراجعة عند التصحيح.

### د. التشغيل المؤسسي

`طلب/مهمة ← تعيين مسؤول ← تحديد موعد معتمد ← تنفيذ ← دليل إنجاز ← مراجعة ← اعتماد ← تقرير ← إغلاق`

يجب أن تسجل المهمة رقمًا فريدًا، والمجال، والأولوية، والمسؤول البشري، والمركز/الفرع، والحالة، وموعد الاستحقاق المعتمد، والدليل، ومراجع الجودة، والاعتماد النهائي عند الحاجة.

## 5. إنجازات وتقارير وإحصاءات قابلة للتدقيق

تُستخرج الأرقام من قاعدة البيانات أو واجهة API المعتمدة؛ لا تُحسب الطلبات المرفوضة أو الاختبارات السلبية باعتبارها قبولًا، ولا تُستخدم القوالب الفارغة بوصفها سجلات إنجاز.

### المؤشرات التشغيلية المقترحة

- **الطلبات المستلمة:** عدد معرفات الطلبات المميزة خلال الفترة، مع فصل حسب الخدمة والفرع.
- **الطلبات المكتملة:** الطلبات التي استوفت الحقول والموافقات المطلوبة.
- **معدل الاستكمال:** الطلبات المكتملة ÷ الطلبات المستلمة × 100، مع بيان الفترة ونطاق البيانات.
- **الطلبات قيد المعالجة:** الطلبات التي حالتها مفتوحة حسب تعريف حالات النظام المعتمد.
- **مدة المعالجة:** متوسط زمن الإغلاق ناقص وقت الإنشاء للطلبات المغلقة؛ تعرض الوسيط أيضًا إذا توفرت العينة الكافية.
- **حضور المتعلمين:** سجلات الحضور المؤكدة ÷ جلسات المتعلمين المستحقة حسب سياسة الحضور.
- **إنجاز الواجبات:** التسليمات المسجلة ÷ الواجبات المستحقة للفئة المقاسة.
- **تقدم التعلم:** وفق قواعد القياس المعتمدة للمقرر، مع تجنب دمج مقاييس مختلفة في رقم واحد.
- **حمل المعلمين:** عدد الحصص المسندة لكل معلم في الأسبوع ومقارنته بالقاعدة المعتمدة للتعليم الأساسي والعام وهي 30 حصة أسبوعيًا لكل عضو تعليمي.
- **مؤشرات الجودة:** عدد الاختبارات الناجحة والفاشلة والمحجوبة، والتنبيهات المفتوحة والمغلقة، والمدة حتى المعالجة.
- **مؤشرات التقنية:** حالة النشر، نجاح فحوص الصحة، استجابة نقاط النهاية، الأخطاء المجمعة، وحالة النسخ الاحتياطية/اختبار الاستعادة عند توثيقها.

كل تقرير يجب أن يوضح: تاريخ الاستخراج، الفترة، مصدر البيانات، المرشحات، تعريف المؤشر، حالة اكتمال المصدر، والجهة المسؤولة. إذا لم تتوفر بيانات موثوقة، تظهر النتيجة «غير متاحة» مع السبب بدل اختلاق رقم أو عرض صفر مضلل.

### التقارير الدورية

- يومي: الطلبات الجديدة والمتأخرة، الحالات التي تنتظر إجراء، وأعطال الخدمة.
- أسبوعي: تقدم المقررات والحضور والواجبات والحمل الأسبوعي ومعالجة الطلبات.
- شهري: أداء البرامج والفروع والجودة والموارد المالية والإدارية والاتجاهات.
- عند الحدث: حادث أمني أو تقني، تغيير إصدار، انقطاع، شكوى جسيمة، أو قرار إداري مؤثر.

## 6. مهام التشغيل المتكررة

### كل يوم عمل
- التحقق من حالة الموقع وواجهات الصحة وكتالوج الخدمات.
- مراجعة الطلبات الجديدة وأعمارها وحالتها والمسؤول الحالي.
- التأكد من أن كل طلب مكتمل له مسار متابعة واضح، دون قبول تلقائي.
- مراجعة مهام اليوم والجداول والفصول والتنبيهات الأكاديمية.
- توثيق الاستفسارات والملاحظات والحوادث في السجل المناسب.
- التحقق من عدم وجود نشر خارجي أو إجراء مالي أو تعديل حساس بلا اعتماد.

### كل أسبوع
- تدقيق الحضور والواجبات والدرجات التي تنتظر المراجعة.
- تدقيق الجداول والحصص وحمل المعلمين وحدود الفروع.
- مراجعة الحسابات والصلاحيات والحسابات التي لم تعد بحاجة إلى الوصول.
- مراجعة قائمة الطلبات المتأخرة وأسباب التعطل وتعيين المسؤول عن كل إجراء.
- ملخص جودة وتشغيل من البيانات المؤكدة، مع قائمة قرارات مطلوبة من الإدارة.

### كل شهر أو قبل أي إصدار
- مراجعة سجل تغييرات البرمجيات والنشر ونتائج الاختبارات.
- مراجعة قاعدة البيانات والمستشار الأمني/الأدائي وتحليل الأولويات.
- التحقق من اكتمال النسخ الاحتياطية وتجربة الاستعادة في بيئة آمنة.
- اختبار مسار تسجيل الدخول والتفويض والعزل بحسابات اختبار منفصلة.
- مراجعة السياسات والنماذج والنصوص القانونية ومعلومات البرامج.
- اختبار التوافق على الهاتف والحاسوب وإمكانية القراءة واتجاه RTL.
- حفظ تقرير إصدار يتضمن الالتزام البرمجي والاختبارات والنشر والملاحظات المفتوحة.

## 8. أمن البيانات وحماية الاستمرارية

- لا تُحذف سجلات أو مشاريع أو طلبات قائمة كوسيلة لإصلاح الاختبارات.
- لا تُجرى اختبارات قبول تكتب في قاعدة الإنتاج إذا كانت قادرة على إنشاء سجلات فعلية؛ تستخدم بيئة اختبار مستقلة وحسابات اصطناعية.
- لا تُكشف قيم الأسرار أو رموز الوصول أو مفاتيح التوقيع في التقارير أو شيفرة العميل أو رسائل الدعم.
- لا تنقل وحدات التشغيل من Supabase إلى Neon أو بالعكس دون جرد اعتماديات واختبار توافق وخطة رجوع موثقة.
- يستمر استخدام قواعد البيانات الحالية حتى التحقق من الجداول وواجهات API والصلاحيات ومكان كل فئة من البيانات.
- تبقى المرفقات الخاصة معطلة حتى إثبات صلاحيات التخزين والعزل والتحقق من نوع الملف وحجمه.
- لا تُمنح صلاحية «مدير» بمجرد إخفاء زر أو معرفة رابط؛ يجب أن يفرض الخادم التفويض على كل إجراء حساس.
- تحفظ سجلات التدقيق على نحو لا يسمح لمستخدم عادي بتغيير تاريخ القرارات أو محو أثر الإجراءات.
- تستخدم أقل صلاحية ممكنة لكل دور، وتُراجع السياسات التي تسمح بأكثر من مسار قراءة/كتابة.
- تتم تجربة الاستعادة دون الكتابة فوق قاعدة الإنتاج أو استبدال بياناتها.

## 9. نقاط Supabase التي تحتاج متابعة موجهة

أظهر آخر فحص للمستشار:
- تحذيرين لدوال `SECURITY DEFINER` قابلة للتنفيذ من الدور authenticated: `act_on_edu_directive` و`create_edu_directive`.
- تحذيرًا بأن حماية كلمات المرور المسرّبة غير مفعّلة.
- نتائج أداء أشارت إلى 153 مفتاحًا أجنبيًا دون فهرس تغطية، و91 فهرسًا لم يظهر له استخدام، و19 حالة لسياسات RLS سماح متعددة.

لا تُجرى تغييرات جماعية أو حذف للفهارس اعتمادًا على هذه الأعداد وحدها. الخطوات المطلوبة هي فحص تعريف الدالة والسياسات التي تنطبق عليها، وإثبات التفويض داخل الإجراء، وقياس استعلامات العمل الفعلية، ثم تطبيق تغيير صغير ومراجع واختباره. المراجع:
- https://supabase.com/docs/guides/database/database-linter
- https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection
