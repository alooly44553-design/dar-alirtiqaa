# منظومة الارتقاء الفكري الصحية
## المرجع التنفيذي النهائي لنطاق العمل والتشغيل والجاهزية

**تاريخ المراجعة:** 24 أكتوبر 2026  
**الغرض:** توحيد نطاق المنظومة الصحية، وأدوار المستخدمين، والخدمات، ومسارات الطلبات، والتشغيل، والتقارير، والأمان، ومعايير الإطلاق.  
**حالة الوثيقة:** مرجع تنفيذي للتنفيذ والتحقق والاعتماد؛ لا يثبت وحده أن كل ميزة قد نُفذت أو اجتازت الاختبارات.

## 1. الملخص التنفيذي وحقيقة الجاهزية

يوجد تطبيق ويب مستقل للمراكز الصحية، ونشر إنتاجي في Vercel، وصفحات تشغيل وتنظيم وإعلان صحي، ولوحة إدارة، وواجهات خادمية تستخدم مصادقة Neon Auth وتتحقق من بعض صلاحيات الإدارة، وقاعدة بيانات مخصصة للمشروع. توجد أيضًا واجهات أولية للمواعيد والطلبات والخدمات الإدارية.

**التصنيف التشغيلي الحالي: منشور تقنيًا، لكنه غير معتمد بعد للتشغيل الصحي الإنتاجي الشامل.** سجل المستودع يوضح أن أقسامًا من التطبيق تحفظ البيانات في متصفح الجهاز محليًا ولا تتزامن بين المستخدمين أو الفروع، وأن استكمال تكامل جميع النماذج مع قاعدة البيانات واختبارات المصادقة والعزل والنسخ الاحتياطي ما زال شرطًا قبل التشغيل الكامل. كما أن استقبال المواعيد عبر الإنترنت مقيد ببوابة تفعيل، ولا يجوز فتحها قبل التحقق من مسار المراجعة الإدارية وإشعار الخصوصية.

### حالات العمل المعتمدة في هذا المرجع

- **موجود في المستودع:** ملف أو مسار أو واجهة يمكن فحصها.
- **موجود جزئيًا:** توجد واجهة أو API أو قاعدة بيانات، لكن دورة العمل الكاملة لم تُثبت.
- **بحاجة إلى تكامل:** يعتمد على مزود أو إعداد أو قاعدة بيانات أو حساب خارجي لم يثبت عمله من طرف إلى طرف.
- **بحاجة إلى اعتماد:** يتطلب قرارًا إداريًا أو مراجعة خصوصية أو مراجعة طبية/نظامية.
- **متحقق:** اجتاز اختبارًا محددًا موثقًا على النسخة والبيئة المعنيتين.
- **موقوف احترازيًا:** لا يُفتح للمستخدمين قبل إغلاق شروط الأمان والتشغيل.

لا يُنقل أي بند إلى حالة «متحقق» اعتمادًا على وجود واجهة أو بناء ناجح أو نشر بحالة READY فقط.

## 2. الرؤية والحدود المهنية

### الرؤية

إنشاء منظومة إدارية وتشغيلية موحدة لمراكز الارتقاء الفكري الصحية، تدعم استقبال طلبات الخدمة غير السريرية، وتنظيم المواعيد والتجهيزات والطاقم والمهام، ومتابعة جودة التشغيل، وإنتاج تقارير إدارية قابلة للمراجعة، مع حماية المعلومات وتحديد واضح للمسؤوليات.

### الغرض التشغيلي

1. توحيد إجراءات استقبال المستفيدين وتسجيل طلباتهم ومتابعتها.
2. تقليل الاعتماد على الملفات المحلية المتفرقة والجداول اليدوية غير المتزامنة.
3. ضبط صلاحيات العاملين حسب المركز والدور والمسؤولية.
4. قياس سرعة الاستجابة وجودة الخدمة وإنجاز المهام.
5. إنشاء سجلات تدقيق موثقة لكل إجراء إداري مؤثر.
6. توفير آلية للإشراف والتحسين المستمر والتعامل مع الشكاوى والحوادث.
7. توفير أساس تقني قابل للتوسع دون خلط البيانات الصحية بسجلات المشاريع التعليمية أو العامة الأخرى.

### الحد الفاصل بين الإدارة والرعاية السريرية

هذا المرجع يجهز منظومة التشغيل الإداري والمواعيد والطلبات والمراكز والموظفين والتجهيزات والتقارير غير السريرية. ولا يحول التطبيق تلقائيًا إلى نظام سجل طبي إلكتروني.

إلى أن يعتمد نطاق سريري رسمي وتُنَفَّذ ضوابطه، يجب عدم جمع أو تخزين التشخيصات، أو الوصفات، أو نتائج المختبر، أو الصور الطبية، أو ملفات المرضى، أو تفاصيل التاريخ المرضي في نماذج التشغيل العامة أو التخزين المحلي. لا يقدم المساعد الذكي تشخيصًا أو قرار علاج أو وصفة دوائية، ولا يحل محل الطبيب أو الممارس المرخص.

يجب أن تتحقق الإدارة المختصة من تراخيص المركز والممارسين والخدمات في الولاية النظامية ذات الصلة قبل الإعلان عن تقديم خدمة صحية سريرية بعينها. لا تمثل هذه الوثيقة إثباتًا لترخيص أو شراكة حكومية أو اعتماد طبي.

## 3. الهيكل التنظيمي والأدوار والصلاحيات

الصلاحية لا تُمنح بناءً على رابط الصفحة أو إخفاء زر في الواجهة. يجب التحقق منها في الخادم في كل طلب، وحصرها في أقل مستوى لازم لأداء العمل، وربط بيانات الموظف بمركز واحد أو نطاق مراكز معتمد.

### أ. الأدوار الأساسية

| الدور | نطاق المسؤولية | الصلاحيات الأساسية | القيود |
|---|---|---|---|
| مالك المنظومة | الحوكمة وإدارة النطاق الكلي | اعتماد الإعدادات الحساسة، إدارة مسؤولي المنظومة، اعتماد تفعيل المراكز، الاطلاع على التقارير الشاملة وسجل التدقيق | لا يُستخدم الحساب اليومي المشترك؛ تتطلب الإجراءات الحرجة تحققًا إضافيًا وسجلًا |
| مسؤول المنظومة | إدارة المراكز والطاقم والطلبات | إنشاء مراكز كمسودات، إدارة حسابات الموظفين وأدوارهم، مراجعة الطلبات، إعدادات التشغيل المصرح بها | لا يطّلع تلقائيًا على بيانات سريرية غير مطلوبة لعمله |
| مدير المركز | إدارة مركز محدد | متابعة طاقم مركزه وطلباته ومهامه وتجهيزاته وتقاريره | يُمنع من الوصول إلى سجلات مركز آخر إلا بتفويض واضح |
| موظف الاستقبال/تنسيق المواعيد | استقبال الاستفسارات والمواعيد غير السريرية | مراجعة الحد الأدنى من بيانات الطلب، طلب استكمال البيانات، اقتراح موعد، تأكيده أو إلغاؤه وفق الإجراء المعتمد | لا يضيف تشخيصًا ولا يطلع على سجل طبي غير مخول |
| منسق الخدمات | متابعة طلبات الخدمات غير السريرية | فرز الطلبات، إحالتها للجهة الداخلية، متابعة المهل، توثيق الإغلاق | لا يصدر موافقة مهنية أو طبية أو قانونية خارج صلاحياته |
| مسؤول العمليات والمرافق | التجهيز والصيانة والمخزون | إدارة المهام والأصول والمخزون والتنبيهات ومحاضر الصيانة | لا يدخل بيانات المرضى في سجل الأصول أو الصيانة |
| مسؤول الجودة والسلامة | التدقيق والتحسين والحوادث | مراجعة مؤشرات الجودة، فتح إجراء تصحيحي، متابعة الإغلاق، إدارة سجل الحوادث المصرح به | لا يحذف أدلة التدقيق؛ تُحجب تفاصيل الهوية بحسب الحاجة |
| الممارس الصحي المرخص | الرعاية المهنية ضمن نطاق الترخيص | دور مستقبلي يحدد بعد اعتماد النظام السريري، وتوثيق الترخيص والتخصص والصلاحيات | غير مفعّل بوصفه دورًا سريريًا كاملًا بهذه الوثيقة؛ لا تُمنح له ميزات غير مبنية ومختبرة |
| مسؤول الخصوصية وحماية البيانات | الموافقات والاحتفاظ وطلبات أصحاب البيانات | مراجعة الإشعارات، متابعة طلبات الخصوصية، مراجعة الوصول وسجل التدقيق | لا يطّلع على المحتوى الصحي التفصيلي إلا عند ضرورة موثقة |
| المراجع/المدقق | الرقابة المستقلة | قراءة السجلات والتغييرات والتقارير التي يسمح بها نطاق التدقيق | قراءة فقط؛ لا ينشئ أو يعدل أو يعتمد الطلبات |
| الدعم التقني | استكشاف الأخطاء واستمرارية النظام | مراقبة التوافر، التشخيص الفني، إدارة الإصدارات والتكاملات وفق التفويض | لا يتصفح بيانات المستفيدين أو يصدّرها كجزء من الدعم الاعتيادي |
| المستفيد/مقدم الطلب | طلب الخدمة ومتابعة الاستجابة | إرسال طلب محدود البيانات، تلقي رقم مرجعي، طلب تحديث أو إلغاء وفق السياسة | إرسال الطلب لا يعني قبولًا أو حجزًا مؤكدًا أو تقديم خدمة طبية |

### ب. الأدوار التي تظهر في البناء الحالي

تظهر واجهات الإدارة الحالية أدوارًا إدارية مثل مالك المنظومة ومسؤول المنظومة والمدقق، مع أدوار للعاملين بالمراكز مثل المدير والموظف والمشاهد. يجب مطابقة الأسماء الفعلية والامتيازات في قاعدة البيانات مع الجدول أعلاه قبل فتح أي حساب جديد. أما أدوار الممارس السريري ومسؤول الخصوصية ومنسق الاستقبال ومسؤول العمليات المتخصص فهي تصنيفات مطلوبة للتخطيط، ولا تُعتبر مفعلة ما لم توجد لها صلاحيات خادمية واختبارات منفصلة.

### ج. ضوابط الحسابات

1. حساب فردي لكل موظف؛ يمنع الحساب المشترك.
2. تحقق آمن من البريد أو عامل الدخول المعتمد، وآلية استعادة حساب موثقة.
3. لا ينشئ إثبات البريد وحده صلاحية إدارية ولا يفعّل حسابًا غير معتمد.
4. تُسجل عملية منح الدور وتغييره وتعطيله مع المنفذ والوقت والسبب.
5. تُراجع الصلاحيات دوريًا وعند النقل أو انتهاء العلاقة الوظيفية.
6. تُنهى الجلسات أو تُسحب صلاحية الحساب عند الاشتباه في اختراقه.
7. لا تُستخدم بيانات المستخدم الوصفية القابلة للتعديل من المستخدم نفسه لتحديد الصلاحية.
8. يُنفذ فحص سلبي يثبت أن كل دور لا يستطيع قراءة سجل خارج نطاقه أو تغيير صلاحية نفسه.

## 4. وحدات المنظومة ومسؤولية كل وحدة

| دليل المراكز والفروع | الاسم والرمز والمنطقة وحالة المركز وقنوات التواصل | سجل مركز موثوق وحالة مسودة/نشط/موقوف |

| البرامج والأنشطة التوعوية | خطة النشاط والهدف والجمهور والمسؤول والميزانية المعتمدة عند الحاجة | خطة ومخرجات وتقييم نشاط |

| التقارير والإحصاءات | مقاييس تشغيلية مع فلاتر زمنية ومركزية | تقرير مجمع قابل للتصدير دون كشف زائد للبيانات |

| حالة الجاهزية | فحوص الاتصال والتكامل والاختبارات والمتطلبات المفتوحة | لوحة حقيقة الجاهزية: ناجح/فاشل/غير مختبر |

| نسخ احتياطي واستعادة | حماية قاعدة البيانات وإثبات إمكانية الاستعادة | نسخ مجدولة ونتيجة اختبار استعادة موثق |

ينبغي عدم عرض أي وحدة على أنها متصلة مركزيًا إذا كانت تعتمد حاليًا على localStorage أو تنزيل ملف CSV أو إدخال يدوي محلي.

## 5. مسارات التشغيل الأساسية

### المسار 1: طلب موعد غير سريري

1. يفتح المستفيد صفحة الطلب العامة.
2. يعرض النموذج غرض الخدمة وبيانات التواصل الضرورية وإشعار الخصوصية.
3. لا يُقبل الطلب دون موافقة واضحة على الإشعار المعروض.
4. يتحقق الخادم من الطريقة والحقول والتاريخ والوقت والحجم ومصدر الطلب ومعدل الإرسال.
5. ينشأ الطلب بالحالة «جديد» فقط بعد نجاح الحفظ في قاعدة البيانات.
6. تظهر للمستفيد رسالة استلام ورقم مرجعي إذا كان المسار يدعم ذلك.
7. يراجع موظف مخول الطلب من لوحة الإدارة؛ لا يُرسل تأكيد حجز نهائي آليًا بمجرد الاستلام.
8. يختار الموظف «تأكيد» أو «إلغاء» أو «استكمال معلومات»، مع تسجيل المنفذ ووقت الإجراء.
9. يُشعر المستفيد عبر قناة مفعلة ومصرح بها؛ وإلا يتواصل الفريق بالطريقة المعتمدة يدويًا.
10. بعد الموعد، تُسجل حالة الإكمال أو الإلغاء وفق إجراء موثق.

**نطاق البيانات:** الاسم، وسيلة التواصل، التخصص المطلوب أو نوع الخدمة، التاريخ/الوقت المفضل، الموافقة، الحالة، ووقت الإنشاء. لا تُضاف حقول التشخيص أو وصف الأعراض إلى نموذج المواعيد الإداري.

**حالات الطلب:** جديد ← قيد المراجعة عند الحاجة ← مؤكد أو ملغى ← مكتمل. ويُسجل عدم الحضور كحالة إضافية فقط بعد اعتمادها وتنفيذها في المخطط والواجهة.

### المسار 2: طلب خدمة إداري

1. يستقبل النموذج طلبًا محدود البيانات.
2. ينشأ رقم مرجعي فريد ويُحفظ نوع الخدمة وتاريخ الاستلام.
3. يُسند الطلب لمسؤول أو وحدة، ويظهر في قائمة الانتظار.
4. تراجع الوحدة اكتمال المتطلبات، وتطلب النواقص من المستفيد عند الحاجة.
5. يُتخذ قرار مخول: قبول، رفض مع سبب إداري مناسب، أو استمرار المراجعة.
6. تسجل المتابعة ومهلة الإنجاز وآخر إجراء.
7. لا يُغلق الطلب إلا عند توثيق النتيجة أو سبب الإغلاق.
8. تدخل النتائج في مؤشرات الأداء والتقارير دون إظهار تفاصيل اتصال مقدم الطلب لغير المخولين.

**حالات مقترحة:** جديد، قيد المراجعة، مقبول، مرفوض، مكتمل. لا تعد هذه الحالات قرارًا طبيًا أو ضمانًا للحصول على خدمة خارج صلاحيات المركز.

### المسار 3: إنشاء مركز أو تعديله

1. ينشئ مسؤول مخول مركزًا بحالة «مسودة».
2. تُراجع بيانات الاسم والرمز والمنطقة والتواصل والخدمات المحددة.
3. يتحقق المسؤول المختص من الوثائق والاشتراطات والتراخيص خارج حدود التطبيق.
4. يُسجل قرار الاعتماد الداخلي مع مرجع المستند المعتمد.
5. لا يتحول المركز إلى «نشط» إلا بعد الموافقة واجتياز قائمة الجاهزية.
6. يمكن إيقاف المركز مع تسجيل السبب والوقت والمنفذ، دون حذف سجلاته التاريخية.

### المسار 4: إضافة موظف وربط هويته

1. ينشئ مسؤول مخول ملفًا وظيفيًا إداريًا بالحد الأدنى من البيانات.
2. يحدد المركز والدور وفق مصفوفة الصلاحيات.
3. يُرسل الموظف إلى مسار المصادقة الرسمي.
4. تُربط الهوية بعد التحقق من الحساب، وليس بمجرد تشابه الاسم أو البريد المدخل.
5. يبقى الحساب غير مفعل حتى يستوفي متطلبات الاعتماد.
6. يجرى اختبار وصول بدور الموظف واختبار منع الوصول إلى مركز آخر.
7. تسجل كل عملية ربط أو تفعيل أو تعطيل في سجل التدقيق.

### المسار 5: المهمة التشغيلية أو الصيانة

1. ينشئ المسؤول مهمة بعنوان وهدف واضح وأولوية وموعد ومسؤول.
2. ينتقل التكليف إلى «مفتوحة»، ثم «قيد التنفيذ».
3. يرفق المسؤول مرجعًا غير حساس أو نتيجة تحقق.
4. يطلب الموظف الاعتماد عند الحاجة.
5. تُغلق المهمة بعد تحقق المسؤول المخول من النتيجة.
6. تسجل المهام المتأخرة وأسباب التأخير والإجراءات التصحيحية.

**الحالات:** مفتوحة، قيد التنفيذ، مكتملة، ملغاة. الإلغاء لا يمحو المهمة من السجل.

### المسار 6: شكوى أو حادث تشغيلي

1. يستقبل البلاغ في قناة محددة.
2. ينشأ معرف حالة وتُحدد درجة الخطورة دون إفراط في البيانات الشخصية.
3. تُحال الحالة فورًا إلى المسؤول المختص بحسب الخطورة.
4. تُتخذ إجراءات الاحتواء الأولية حسب السياسة المعتمدة.
5. يُسجل الإجراء التصحيحي والمسؤول والموعد والأدلة في مخزن محمي.
6. يراجع مسؤول الجودة النتيجة ويعتمد الإغلاق.
7. لا تتضمن سجلات التطبيق العامة تفاصيل طبية أو كلمات مرور أو أسرارًا أو بيانات حساسة غير لازمة.

### المسار 7: نشر محتوى صحي توعوي

1. يكتب المسؤول مسودة محددة الجمهور والغرض.
2. يُتحقق من مصدر المعلومات وتاريخ صلاحيته وحدود النص.
3. يراجع محتوى الادعاءات الطبية مراجع مختص مخول عند الحاجة.
4. تعتمد الإدارة الصيغة والقناة والموعد.
5. لا يجري النشر الخارجي إلا إذا كانت القناة متصلة فعلًا والصلاحية متاحة.
6. يسجل رابط المنشور الحقيقي ووقت النشر والنتائج.
7. لا تعد المسودة المحلية أو زر «تصدير» دليلًا على نشر خارجي.

## 6. المعمارية والبيانات

### المبدأ البنيوي

- الواجهات العامة تجمع أقل قدر من البيانات اللازم.
- الخادم يتحقق من المدخلات والهوية والصلاحية والنطاق قبل القراءة أو الكتابة.
- قاعدة البيانات الصحية مستقلة منطقيًا عن قواعد المشاريع الأخرى.
- لا تحوي ملفات الواجهة العامة أسرار الاتصال أو مفاتيح ذات امتيازات.
- لا تُعطّل خدمة قائمة أو تنقل البيانات من نظام قديم إلى جديد دون مراجعة التبعيات وخطة ترحيل واستعادة.
- تتطلب أي إضافة مخططًا واضحًا ومراجعة أمنية واختبارات توافق، مع سجل تغييرات قابل للمراجعة.

### السجلات المرجعية

تشير قاعدة الشيفرة الحالية إلى جداول لإدارة المراكز والطاقم والإدارة وسجل التدقيق، وإلى مخطط صحي يتضمن طلبات المواعيد والخدمات والمهام والوثائق. يجب فحص المخطط الفعلي ومقارنته بكل استعلام API قبل اعتماد المصفوفة النهائية؛ أسماء الجداول في الوثائق ليست وحدها دليلًا على أن كل جدول حاضر ومحدث في بيئة الإنتاج.

### قواعد سلامة البيانات

1. استخدام معرفات داخلية ثابتة لكل مركز وموظف وطلب ومهمة.
2. ربط كل سجل تشغيلي بالمركز المالك له حيث ينطبق ذلك.
3. تخزين الطوابع الزمنية مع المنطقة الزمنية أو معيار UTC ثم العرض وفق المنطقة المعتمدة.
4. وضع قيود قاعدة بيانات على القيم المسموح بها والحالات والمراجع الأساسية.
5. تطبيق فهارس على الحقول المستخدمة في البحث والتقارير بحسب خطة الاستعلام.
6. عدم الاعتماد على اسم المستفيد أو البريد وحده كمفتاح ربط.
7. عدم جمع بيانات سريرية في مخطط الطلبات العامة.
8. منع حذف السجلات التاريخية كطريقة لتغيير الحالة؛ يستخدم الإلغاء أو الأرشفة المصرح بها.
9. تسجيل الإجراء الإداري المؤثر قبل عرض رسالة نجاح للمستخدم.
10. إذا فشل الحفظ، تظهر رسالة خطأ صريحة ولا يُعرض الطلب على أنه استُلم.

## 7. الأمن والخصوصية واستمرارية الخدمة

### المصادقة والتفويض

- التحقق من صحة رمز الجلسة وتوقيعه ومصدره وانتهاء صلاحيته في الخادم.
- التحقق من الدور والحساب النشط والمركز الفعلي في كل عملية حساسة.
- منع تجاوز الصلاحيات بتعديل عنوان الطلب أو معرف السجل.
- عدم استخدام بيانات قابلة للتعديل من المستخدم نفسه كأساس للصلاحيات.
- عدم إظهار بيانات الاتصال أو سجل التدقيق في API عامة.
- استخدام جلسات قصيرة نسبيًا للعمليات الحساسة وخطة لإبطال الجلسات عند الحاجة.

### حماية بيانات الطلبات

- تشفير النقل عبر HTTPS.
- عدم حفظ المعلومات الصحية الحساسة في localStorage أو ملفات CSV أو سجلات المتصفح.
- إبقاء المرفقات معطلة حتى وجود تخزين خاص وعزل وصول مثبت وروابط مؤقتة حيث يلزم.
- تقليل البيانات الظاهرة في الإشعارات والتقارير.
- تنظيف سجل الأخطاء من الأسماء وأرقام الاتصال ومحتويات الطلبات ومعرّفات الجلسات.
- تحديد مدة احتفاظ معتمدة، وأساس المعالجة، وحق الوصول والتصحيح والحذف حيث ينطبق النظام.
- توثيق كيفية تقديم شكوى خصوصية أو طلب متعلق بالبيانات والجهة المسؤولة عن الاستجابة.
- اعتماد إشعار الخصوصية وشروط الاستخدام من المسؤول القانوني/المختص قبل الإطلاق العام؛ النسخ المسودة لا تعد اعتمادًا نهائيًا.

### مقاومة إساءة الاستخدام

- حصر طرق HTTP حسب المسار.
- وضع حد لحجم الجسم المدخل وتنظيف المدخلات والتحقق من نوعها.
- منع الطلبات المتكررة وفق حد معدل موثق، مع تجربة اختبار عدم حظر المستخدمين الشرعيين.
- تقييد الإرسال من المتصفح وفق سياسة أصل الطلب، وعدم الاعتماد على فحص الأصل وحده كوسيلة مصادقة.
- استخدام حقل honeypot أو وسائل مكافحة إساءة استخدام مناسبة دون تخزين بياناتها.
- إخراج رسائل خطأ لا تكشف SQL أو أسماء الأسرار أو تفاصيل البنية الداخلية.

### النسخ الاحتياطي والاستعادة

- تعيين مسؤول واضح عن النسخ الاحتياطي وتكراره وفترة الاحتفاظ به.
- التحقق من أن النسخ تشمل قاعدة البيانات ومخططها والإعدادات الضرورية، لا الملفات العامة وحدها.
- اختبار الاستعادة في بيئة منفصلة وعدم تجربة الاستعادة على قاعدة الإنتاج.
- تسجيل التاريخ والنطاق والنتيجة والمدة والمسؤول.
- وضع هدف مقبول لفقد البيانات ووقت الاستعادة واعتمادهما إداريًا.
- لا تعتبر قاعدة البيانات جاهزة إنتاجيًا حتى تثبت استعادة صالحة من نسخة احتياطية.

## 8. التقارير والإحصاءات ومؤشرات الأداء

تعرض لوحة المؤشرات بيانات مجمعة بحسب الفترة والمركز والخدمة والحالة، مع صلاحيات وصول، وتوضح وقت تحديث التقرير. يجب ألا تكشف شاشة إحصائية عامة أسماء المستفيدين أو أرقام هواتفهم أو تفاصيل غير لازمة.

| المؤشر | طريقة القياس | الاستخدام الإداري |
|---|---|---|
| الطلبات المستلمة | عدد الطلبات الجديدة خلال الفترة | قياس حجم الطلب |
| الطلبات قيد المراجعة | العدد في الحالة الحالية | تحديد تراكم الأعمال |
| معدل الاستجابة في الوقت المستهدف | الطلبات التي بدأت معالجتها داخل المهلة ÷ الطلبات المستحقة خلال الفترة | متابعة سرعة الفريق |
| متوسط زمن أول استجابة | متوسط الفرق بين وقت الإنشاء وأول إجراء موثق | مراقبة مستوى الخدمة |
| معدل تأكيد المواعيد | المواعيد المؤكدة ÷ طلبات المواعيد الصالحة التي اتخذ فيها قرار | متابعة تحويل الطلب إلى موعد |
| معدل الإلغاء | المواعيد الملغاة ÷ الطلبات التي وصلت إلى حالات قرار نهائي ذات صلة | تحديد أسباب الإلغاء |
| معدل إكمال الطلبات | الطلبات المكتملة ÷ الطلبات التي أغلقت خلال الفترة | تقييم الإنجاز |
| الأعمال المتأخرة | المهام المفتوحة بعد موعد الاستحقاق | توجيه المسؤولين |
| إكمال المهام في موعدها | المهام المكتملة في/قبل الاستحقاق ÷ المهام المكتملة ذات الموعد | إدارة الالتزام |
| جاهزية الطاقم | عدد الحسابات الوظيفية النشطة والمربوطة بهوية معتمدة ضمن النطاق | منع بقاء حسابات غير مرتبطة |
| حالة المراكز | الأعداد حسب مسودة/نشط/موقوف | متابعة التوسع |
| صيانة الأصول | المهام الوقائية المتأخرة، والأصول المبلغ عن خللها | تخطيط الصيانة |
| تنبيه المخزون | الأصناف التي بلغت حد إعادة الطلب وفق الصنف المعتمد | التخطيط للإمداد |
| نتائج التدقيق | حالات غير محسومة حسب الخطورة والعمر | توجيه إجراءات التصحيح |
| شكاوى المستفيدين | العدد والحالة ومتوسط زمن الإغلاق | تحسين تجربة الخدمة |
| توافر النظام | نسبة نجاح فحوص الاستعداد إلى إجمالي الفحوص خلال الفترة | مراقبة الخدمة التقنية |

### قواعد احتساب المؤشرات

1. يعرّف لكل مؤشر مالك بيانات ومصدر ووقت تحديث وطريقة احتساب.
2. تُستبعد السجلات التجريبية بوسم واضح ولا تختلط بطلبات المستفيدين الفعلية.
3. لا تُستخدم أعداد أفراد الطاقم أو طلبات الخدمة لادعاء جودة طبية سريرية.
4. لا تُنشر إحصاءات طبية أو نتائج علاجية حتى وجود نظام سريري معتمد وتعريفات وموافقات لازمة.
5. لا يُعرض «صفر طلبات» على أنه نجاح إذا كان استقبال الطلبات معطلًا؛ يجب إظهار حالة الاستقبال في لوحة التقرير.
6. عند غياب البيانات أو التكامل يظهر «غير متاح/لم يختبر» بدلًا من تخمين قيمة.
7. يوثق تصدير التقرير ووقت إنشائه ونطاقه وصاحب الصلاحية عند احتوائه على بيانات مقيدة.

## 9. الإشعارات والتكاملات

- لا يُعتبر وجود زر أو صفحة تكامل دليلًا على الاتصال بمزود خارجي.
- تُربط كل قناة بعد إنشاء حساب مخول وتوفير بيانات اعتماد مخزنة على الخادم والتحقق من صلاحياتها.
- لا توضع مفاتيح سرية أو روابط بدء المضيف الخاصة في واجهة المتصفح.
- أي بريد أو رسالة خارجية تتضمن قرار قبول أو تأكيد موعد يجب أن تعتمد على الحالة الحقيقية المخزنة.
- لا تُرسل إشعارات تلقائية عن موعد قبل نجاح الحفظ واعتماد الحالة.
- تسجل نتيجة الإرسال دون تخزين محتوى حساس غير ضروري.
- يحدد لكل تكامل مسؤول ومالك بيانات وخطة للتعامل مع انتهاء الاعتماد أو فشل المزود.
- يظل إرسال رسائل أو نشر محتوى أو إنشاء اجتماعات عبر منصة خارجية متوقفًا حتى الاختبار والموافقة.

## 10. الاختبارات المطلوبة قبل الإطلاق

### اختبارات تقنية

- [ ] الصفحات العامة وملفات التطبيق وواجهة الإدارة تعيد الاستجابة المتوقعة.
- [ ] فحص الاتصال بقاعدة البيانات يعيد الحالة العامة فقط ولا يعرض بيانات.
- [ ] API المواعيد تقبل POST فقط وترفض الطرق غير المسموحة.
- [ ] رفض الطلب إذا كانت الموافقة غير موجودة أو غير صحيحة.
- [ ] رفض الاسم القصير ورقم الاتصال غير الصحيح والتخصص غير المحدد والتاريخ/الوقت غير الصالحين.
- [ ] رفض التاريخ خارج النطاق المسموح به، مع التحقق من تاريخ اليوم فعليًا.
- [ ] رفض جسم الطلب الأكبر من الحد.
- [ ] تطبيق حد معدل الطلبات والتحقق من استجابته.
- [ ] التحقق من أن عدم تهيئة قاعدة البيانات أو إعداد الاستقبال يعيد خطأ واضحًا ولا يحفظ طلبًا جزئيًا.
- [ ] التحقق من عدم تسرب الأسرار أو بيانات الاتصال في واجهة المستخدم أو السجلات.
- [ ] بناء نسخة الويب من commit واحد معروف وإجراء مراجعة التغييرات.
- [ ] اختبار التوافق على أجهزة الهاتف والحاسوب وإمكانية الوصول واتجاه الكتابة من اليمين إلى اليسار.

### اختبارات المصادقة والصلاحيات

- [ ] الدخول والخروج واستعادة الحساب وانتهاء الجلسة.
- [ ] الحساب غير المعتمد لا يحصل على دور إداري بمجرد إثبات البريد.
- [ ] المراجع يقرأ فقط ولا يستطيع تنفيذ POST أو PATCH غير مخولين.
- [ ] مدير المركز لا يصل إلى مركز آخر بتغيير معرف في الطلب.
- [ ] الموظف غير النشط لا يستطيع تنفيذ أي عملية إدارية.
- [ ] الموظف غير المرتبط بهوية مصادقة لا يستطيع الدخول إلى البيانات.
- [ ] لا يستطيع المستخدم تغيير دوره أو مركزه بتعديل الجسم أو بيانات الواجهة.
- [ ] كل عملية تغيير تُسجل في سجل تدقيق متاح للمخولين فقط.
- [ ] لا يقرأ مستفيد بيانات مستفيد آخر.

### اختبارات التشغيل

- [ ] إنشاء طلب اختبار في بيئة اختبار مستقلة، ومراجعته واعتماده ثم التحقق من ظهور الحالة في قاعدة البيانات.
- [ ] إلغاء طلب اختبار والتحقق من الاحتفاظ بسجل الإجراء.
- [ ] إنشاء مركز اختبار كمسودة، ثم تفعيله بعد تحقق الشروط، ثم إيقافه دون حذف سجله.
- [ ] إنشاء موظف اختبار وربط هوية اختبار وإجراء اختبار منع وصول.
- [ ] إنشاء مهمة اختبار وإغلاقها، والتحقق من التقارير.
- [ ] اختبار عرض مؤشرات التقرير وتصدير تقرير اصطناعي.
- [ ] اختبار استعادة النسخة الاحتياطية في بيئة معزولة.
- [ ] اختبار عودة التشغيل بعد فشل قاعدة البيانات أو مزود المصادقة.
- [ ] عدم إجراء اختبارات إنشاء أو حذف أو تعديل تجريبية على بيانات الإنتاج الحقيقية.

### معيار نتيجة الاختبار

توثق النتيجة لكل اختبار مع: رقم الاختبار، البيئة، إصدار/commit، حساب الاختبار ودوره، النتيجة المتوقعة، النتيجة الفعلية، الدليل المنقح، المسؤول، وقرار الإغلاق. لا يُقبل وصف «نجح» دون دليل قابل للمراجعة.

## 11. خطة التنفيذ بحسب الأولوية

### المرحلة صفر: التثبيت والحماية

- تثبيت نطاق المشروع الصحي ومصدره البرمجي وبيئة الإنتاج الصحيحة.
- تأكيد اتصال قاعدة البيانات المخصصة وعدم خلطها بقواعد المنظومات الأخرى.
- مراجعة الأدوار الحالية وجلسة Neon Auth ومسار التحقق من الهوية.
- إبقاء استقبال المواعيد في وضع الإيقاف حتى التحقق من شروط الإطلاق.
- التحقق من نسخ البيانات الحالية وعدم تنفيذ أي حذف أو نقل غير موثق.
- إنشاء نسخة احتياطية واختبار الاستعادة قبل تغيرات المخطط.

### المرحلة الأولى: المصادقة والإدارة المركزية

- اعتماد حساب مالك واحد موثق ومسؤول احتياطي وفق الحوكمة.
- اختبار إنشاء المراكز وإدارتها وإضافة الموظفين وربط الهوية.
- إثبات عزل الوصول حسب المركز والدور على الخادم.
- مراجعة سجلات التدقيق وتقييد عرضها.
- توثيق الصلاحيات الفعلية وعدم منح ميزات سريرية افتراضية.

### المرحلة الثانية: استقبال الطلبات

- تدقيق API استقبال المواعيد وقيود الطلبات وواجهة الموافقة.
- اعتماد إشعار الخصوصية وبيانات الجهة المسؤولة ووسيلة التواصل والاحتفاظ.
- اختبار مسار استلام الطلب ومراجعته وتغيير حالته وإغلاقه في بيئة اختبار.
- تجهيز شاشة متابعة واضحة للطلبات الجديدة والمتأخرة.
- التحقق من قدرة الفريق على التعامل اليدوي مع الطلبات حتى عند توقف القناة.

### المرحلة الثالثة: مزامنة العمليات والتقارير

- نقل النماذج التشغيلية المطلوبة من الحفظ المحلي إلى APIs المركزية بعد حماية كل نوع من البيانات.
- بناء واجهات خادمية للمهمات والبرامج والمرافق والمخزون والتقارير حيث يلزم.
- إضافة صلاحيات مستقلة لهذه الوحدات بدل إعادة استخدام صلاحية عامة.
- إنشاء تقارير مبنية على المصدر المركزي، مع وقت التحديث وتعريف كل مؤشر.
- الإبقاء على أي وحدة محلية في وضع المسودة وعدم جمع بيانات حساسة عبرها.

### المرحلة الرابعة: التكامل والإطلاق المقيد

- تفعيل قناة واحدة في كل مرة بعد الاختبار.
- إجراء اختبار قبول مستخدم باستخدام حسابات اختبار محددة.
- اختبار الأداء والأمان والتوافر والاستعادة.
- إصدار نسخة محددة مع رقم commit وتوثيق التغييرات وخطة التراجع.
- فتح الخدمة لفئة محدودة ومراقبة الاستجابة والأخطاء ثم التوسع بموافقة الإدارة.

### المرحلة الخامسة: التوسع السريري إن تقرر

أي مشروع للسجل الطبي أو الوصفات أو نتائج الفحوصات أو الاستشارات السريرية يتطلب متطلبات مستقلة، وتقييمًا مهنيًا ونظاميًا، ومصادقة وصلاحيات تفصيلية، وسجلات تدقيق سريرية، واحتفاظًا وحماية أقوى للبيانات، واختبارات سلامة. لا يُعتبر هذا توسعًا تلقائيًا ضمن المرحلة الإدارية.

## 12. قائمة قرار الإطلاق

لا يُفتح استقبال الطلبات الصحي أو يُعلن عن التشغيل الكامل إلا إذا تحققت جميع الشروط ذات الصلة:

- [ ] تأكيد البيئة الإنتاجية ونسخة الكود التي تخدم النطاق الصحي.
- [ ] تأكيد اتصال قاعدة البيانات المحددة وعدم خلطها ببيانات مشاريع أخرى.
- [ ] استكمال المصادقة الفعلية واختبار ربط الحسابات.
- [ ] اعتماد مصفوفة الصلاحيات وعزل المراكز في الخادم.
- [ ] نجاح اختبارات المواعيد والخدمات في بيئة اختبار منفصلة.
- [ ] توفر لوحة إدارة يمكنها مراجعة الطلبات وتغيير حالاتها بصورة موثقة.
- [ ] اعتماد إشعار الخصوصية وشروط الاستخدام والتواصل وسياسة الاحتفاظ.
- [ ] مراجعة صلاحية المركز والخدمات والممارسين من الجهة المختصة عند انطباق ذلك.
- [ ] اعتماد النسخ الاحتياطي وإثبات الاستعادة.
- [ ] إغلاق الثغرات عالية الخطورة وتوثيق استثناءات المخاطر المتبقية.
- [ ] نجاح اختبار الأدوار والعزل والوصول غير المصرح به.
- [ ] تأكيد تشغيل التنبيهات والقنوات الموصولة، أو توثيق أن التواصل يدوي.
- [ ] نجاح المراجعة البصرية واللغوية واختبارات الهاتف.
- [ ] تحديد مسؤول دعم وتشغيل وسلّم تصعيد للطوارئ والأعطال.
- [ ] وجود دليل اختبار وموافقة إطلاق مسجلة من المسؤول المخول.

**نتيجة القرار:**  
- «مرفوض للإطلاق» عند فشل المصادقة أو عزل المراكز أو تخزين البيانات أو حماية الطلبات أو استعادة النسخ الاحتياطية.  
- «إطلاق مقيد» فقط بعد اجتياز بوابة التشغيل غير السريري، مع نطاق خدمة محدود ومراقبة بشرية.  
- «إطلاق عام» بعد اجتياز الاختبارات والاعتمادات والتشغيل المقيد وتوثيق القرار.

## 14. قواعد التغيير والإصدار

1. لا تُحذف أي بيانات أو سجلات أو مشاريع أو سجلات تدقيق كجزء من الإكمال أو الاختبار.
2. لا تنفذ تغييرات مخطط الإنتاج دون مراجعة أثر وخطة استعادة.
3. تنفذ التغييرات في فرع منفصل وتراجع قبل دمجها.
4. لا يُنشر إصدار إنتاجي قبل اختبار النسخة نفسها التي ستُنشر.
5. يُحتفظ بمعرف commit والإصدار وسجل قرارات النشر.
6. عند الفشل يستخدم مسار تراجع محدد ومختبر، دون محو البيانات أو إعادة ضبطها عشوائيًا.
7. لا تُعرض أسرار البيئة أو رموز المصادقة أو مفاتيح الخدمات في الملفات العامة أو الرسائل أو السجلات.
8. لا يعتمد الذكاء الاصطناعي قرارات التوظيف أو التراخيص أو العلاج أو قبول المستفيدين أو الرسوم أو المواعيد النهائية تلقائيًا.
9. لا تسجل ميزة كمكتملة حتى تُختبر فعليًا في بيئة ونسخة محددتين.
10. تُسجل الاستثناءات والقرارات المؤجلة مع مسؤول وسبب وموعد مراجعة.
