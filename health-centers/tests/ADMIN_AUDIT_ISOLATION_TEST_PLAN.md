# خطة اختبارات سجل التدقيق وعزل المراكز

- النطاق: `health-centers` فقط.
- الحالة: خطة اختبار للمراجعة؛ ليست نتيجة تنفيذ أو شهادة أمان.
- البيانات: اصطناعية فقط.
- لا تتصل هذه الخطة بقاعدة الإنتاج ولا تسمح بتغييرها.

## 1. اختبار فشل سجل التدقيق بعد تعديل إداري

### الهدف
منع نتيجة ملتبسة عندما ينجح INSERT/UPDATE الأساسي ثم يفشل INSERT الخاص بسجل التدقيق.

### السيناريوهات
1. عملية تعديل ناجحة مع نجاح سجل التدقيق: يجب أن تكون الاستجابة ناجحة وأن يتوفر سجل التدقيق المتوقع.
2. فشل إدراج سجل التدقيق بعد تعديل المركز: تحقق من أن السياسة المختارة متسقة وقابلة للرصد؛ إذا كانت المعاملة الذرية مدعومة، يجب ألا يبقى التعديل دون سجل تدقيق. إذا تعذر ضمان الذرية، يجب ألا توحي الاستجابة بأن العملية لم تحدث بينما تكون قد حُفظت، ويجب توثيق آلية الاسترداد/التنبيه.
3. فشل سجل التدقيق عند إنشاء موظف أو تغيير دوره/نشاطه أو تحديث طلب: كرر التحقق لكل إجراء يستدعي `audit()`.
4. فشل قاعدة البيانات قبل التعديل: يجب عدم إنشاء سجل تدقيق يوحي بنجاح عملية لم تحدث.
5. لا تتضمن السجلات أو الاستجابات رموز جلسات أو أسرارًا أو بيانات شخصية زائدة.

### متطلبات التنفيذ للاختبار
- استخدم mock/عميل اختبار يمكنه محاكاة فشل إدراج سجل التدقيق تحديدًا، دون أي اتصال بإنتاج.
- لا تكتفِ باختبار الدالة `audit()` وحدها؛ اختبر استجابة الـhandler وحالة التغيير المتوقعة.
- لا تُدخل إصلاحًا إلى `main` ضمن هذا الاختبار. أي تعديل سلوكي يحتاج مراجعة مستقلة واختبارات CI.

## 2. اختبار العزل بين مركزين

أنشئ في قاعدة اختبار معزولة بيانات اصطناعية للمركزين A وB، ومستخدمين اصطناعيين نشطين لكل مركز، ومسؤول منصة اختباري.

لكل endpoint وطريقة مدعومة، تحقق من:
- موظف A لا يستطيع قراءة أو تعديل موظفي B أو بيانات مركز B بتغيير معرفات الطلب.
- موظف B لا يستطيع قراءة أو تعديل موظفي A أو بيانات مركز A.
- لا يستطيع موظف مركز إدارة طلبات المنصة المركزية أو قراءة سجل تدقيق المنصة.
- الحساب المعطل، والهوية غير المرتبطة، وJWT غير الصحيح تُرفض.
- المستخدم غير المخوّل لا يتلقى تفاصيل تكشف وجود سجلات مركز آخر.
- الطلبات المرفوضة لا تُحدث تغييرات جانبية.
- مسؤول المنصة لا يحصل إلا على الصلاحيات المحددة لدوره.

غطِّ على الأقل `GET` لبيانات الإدارة، و`center_update`، و`staff_create`، و`staff_link`، و`staff_update`، و`request_update`، مع كل من الحالات المسموحة والمرفوضة.

## 3. الإعداد والتنفيذ الآمن

1. استخدم قاعدة اختبار مستقلة وبيانات اصطناعية فقط؛ لا تستخدم بيانات حقيقية.
2. اجعل أسرار الاختبار قصيرة العمر ومخزنة في مدير أسرار معتمد؛ لا تكتبها في الملفات أو CI logs.
3. لا تُشغّل migrations على الإنتاج ولا تعدّل إعدادات Vercel/Neon.
4. شغّل `npm run verify` داخل `health-centers`، واحفظ رابط CI والـcommit الدقيق.
5. نفّذ اختبارات التكامل فقط بعد توفير بيئة اختبار مصرح بها ومثبتة؛ اختبارات mocks الحالية لا تثبت عزل الصفوف الفعلي.
6. راجع النتيجة بواسطة شخص آخر قبل الدمج.

## 4. أدلة الإغلاق المطلوبة

- [ ] CI ناجح على commit محدد.
- [ ] نتائج سيناريوهات فشل التدقيق، بما فيها الحالة التي ينجح فيها التعديل ويفشل سجل التدقيق.
- [ ] نتائج عزل مركز A عن B لكل endpoint ذي صلة.
- [ ] دليل أن الطلبات المرفوضة لم تُحدث تغييرًا جانبيًا.
- [ ] نتائج استعادة نسخة احتياطية في بيئة منفصلة.
- [ ] دليل موثوق على مواقع قاعدة البيانات والنسخ الاحتياطية والخدمات التابعة داخل السعودية، ومراجعة الخصوصية/القانون.

## 5. بوابات مستقلة لا تغلقها هذه الخطة

قرار المشروع الموثق يحدد المملكة العربية السعودية فقط. يشير ملف API الحالي إلى نطاق Neon في `ap-southeast-1`؛ لذلك لا يجوز وصف إقامة البيانات بأنها سعودية قبل إثبات موثوق. لا تُنقل البيانات ولا يُختَر بلد بديل تلقائيًا.

هذه الخطة لا تجيز الدمج أو النشر أو تغيير قاعدة البيانات أو فتح استقبال البيانات الحقيقية أو شراء خدمات أو تشغيل تكاملات خارجية.
